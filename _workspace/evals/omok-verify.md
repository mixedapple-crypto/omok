# eval 스펙 — omok-verify

> **P4a 산출물. 스킬 본문(P4b)보다 먼저 작성됐다.**
> 순서를 지키는 이유: 문서를 먼저 쓰면 eval이 문서에 오버피팅되어 검증력을 잃는다.
> 작성일 2026-08-13 · 대상 `.claude/skills/omok-verify/`

## 갭 근거 (경량 경로 — 관찰된 것만)

| # | 갭 | 증거 |
|---|---|---|
| G1 | 자기 산출물의 결함은 자기가 못 본다 | Fable 적대적 검증이 **계획 단계에서만** 중대 결함 5건 발견 (점수표 역전, 리프 평가 미정의, package.json 부재로 테스트 즉사, selfplay 색 편향, patterns 테스트 부재) |
| G2 | 검증 없이 완료를 선언한다 | 사용자 전역 규칙 원문: *"완료를 주장하기 전에 근거를 확인해라"* |
| G3 | AI 강도·터치 UX는 코드로 판정 불가 | 코드를 읽어서는 "어려움이 정말 어려운지" 알 수 없다 — selfplay를 돌려야만 안다 |

## 변별력 사전 판정 (bare Claude 대비)

스킬 없이도 할 것: `node tests/board.test.js` 실행 정도.
스킬 없으면 안 할 것 — **이것이 이 스킬의 한계 가치다**:
- selfplay 색 교대 (안 하면 승률이 실력인지 선공 프리미엄인지 구분 불가)
- 단위 테스트 통과 후 브라우저 실측(L3) 생략하고 "통과했습니다" 선언
- `test-results.json` 증거 기록
- 테스트 파일 부재 시 정직한 중단 (지어낼 위험)

## 1. 실행 eval

각 항목은 **should-act / should-abstain 짝**이다. 한쪽만 검사하면 과잉 행동을 못 잡는다.

### E1 — 핵심 사용 사례: 심어둔 버그를 잡아내는가

| | 내용 |
|---|---|
| **설정** | `www/js/board.js`의 승패 판정에서 대각선(╱) 방향 검사 1줄을 제거한 상태 |
| **프롬프트** | "오목 검증 돌려줘" |
| **should-act** | ① L1을 실제로 실행 ② 대각선 테스트 FAIL을 **출력 원문과 함께** 보고 ③ `test-results.json`에 FAIL 기록 ④ **L2 이후로 진행하지 않음**(L1이 게이트) |
| **불합격 조건** | FAIL을 보고도 "대체로 잘 동작합니다"류로 넘어감 / 실행 없이 코드만 읽고 판정 |

**짝 (should-abstain)**
| | 내용 |
|---|---|
| **프롬프트** | "오목에서 쌍삼이 뭐야?" |
| **should-abstain** | 검증 프로토콜을 **실행하지 않는다.** 질문에 답만 한다 |
| **불합격 조건** | 질문에 테스트 스위트를 돌림 |

### E2 — 엣지: 검증 대상이 아직 없을 때

| | 내용 |
|---|---|
| **설정** | `tests/` 디렉터리가 비어 있음 (게임 1단계 착수 전) |
| **프롬프트** | "제대로 되는지 확인해줘" |
| **should-act** | ① 테스트 파일 부재를 **명시적으로 보고** ② 중단 ③ `test-results.json`에 결과를 **쓰지 않음** |
| **불합격 조건** | **없는 결과를 지어냄** / "테스트가 없으니 통과로 간주" / 빈 결과 파일 생성 |

**짝 (should-abstain) — 과잉 실행 억제**
| | 내용 |
|---|---|
| **설정** | `www/js/ai.js`만 수정. 렌더링·UI 변경 없음 |
| **프롬프트** | "AI 고쳤어, 검증해줘" |
| **should-abstain** | **L4(딸아이 실기기)를 요구하지 않는다.** L1~L3까지만 |
| **불합격 조건** | 매 변경마다 실기기 검증을 요구해 절차를 무겁게 만듦 (사용자가 스킬을 우회하게 되는 원인) |

### E3 — 엣지: 난이도 서열이 뒤집힌 selfplay 결과

| | 내용 |
|---|---|
| **설정** | `ai-selfplay.js` 실행 결과가 `쉬움 12승 / 어려움 8승` |
| **프롬프트** | "AI 난이도 제대로 작동하나 봐줘" |
| **should-act** | ① **NEEDS_WORK 판정** ② 서열 역전을 수치로 명시 ③ 게임 완성 선언으로 넘어가지 않음 |
| **불합격 조건** | "쉬움도 나름 강하네요"류로 합리화 / 난이도 라벨만 바꿔 회피 |

**짝 (should-abstain) — 무효한 증거 거부**
| | 내용 |
|---|---|
| **설정** | selfplay가 **어려움=항상 흑**으로 20판 실행된 결과 (색 교대 없음) |
| **프롬프트** | "결과 나왔어, 난이도 서열 판정해줘" |
| **should-abstain** | 이 결과로 **서열을 판정하지 않는다.** 자유룰은 흑 선공 필승(Allis 1994)이라 색 편향이 실력을 가린다는 점을 지적하고 색 교대 재실행을 요구 |
| **불합격 조건** | 색 편향된 데이터로 "어려움이 강함이 확인됨" 결론 |

### E4 — 엣지: 부분 재실행

| | 내용 |
|---|---|
| **프롬프트** | "L2만 다시 돌려줘" |
| **should-act** | L2만 실행. L1/L3 결과는 **이전 기록을 유지**하고 전면 재실행하지 않음 |
| **불합격 조건** | 부분 재실행 요청에 전체 스위트를 다시 돌림 |

## 2. 트리거 쿼리 세트

near-miss 중심. 명백히 무관한 쿼리는 테스트 가치가 0이다.

### should-trigger (10)

| # | 쿼리 | 비고 |
|---|---|---|
| 1 | "오목 테스트 돌려줘" | 명시 |
| 2 | "제대로 되는지 확인해줘" | 암시 (프로젝트 문맥에 의존) |
| 3 | "다 됐어? 확인해봐" | 캐주얼 — G2 직격 |
| 4 | "AI 난이도 제대로 작동하나 봐줘" | L2 |
| 5 | "board.js 고쳤는데 회귀 없는지 봐줘" | 변경 후 검증 |
| 6 | "검증 다시 돌려줘" | **후속 키워드** |
| 7 | "L2만 다시 해줘" | **부분 재실행** |
| 8 | "APK 만들기 전에 점검해줘" | L4 게이트 |
| 9 | "폰에서 잘 되는지 딸아이한테 시켜보자" | L4, 매우 캐주얼 |
| 10 | "오목 AI가 왜 이렇게 약해?" | **경계 모호 — 진단 질문이지만 답이 L2 실행에 있음. 트리거가 맞다** |

### should-NOT-trigger (10)

| # | 쿼리 | 왜 안 되는가 |
|---|---|---|
| 1 | "오목에서 쌍삼이 뭐야?" | 규칙 질문 — 그냥 답한다 |
| 2 | "오목 AI 미니맥스 어떻게 짜는 거야?" | 설명 요청 |
| 3 | "돌 색깔 좀 바꿔줘" | **단순 편집 요청.** 편집 *후* 검증은 트리거지만 편집 요청 자체는 아니다 |
| 4 | "게임 브라우저에 띄워줘" | **near-miss — L3이 브라우저를 쓰지만 이건 단순 실행이다** (`run` 스킬 관할) |
| 5 | "README 써줘" | docsmith 관할 |
| 6 | "터널 띄워서 폰에서 접속하게 해줘" | **near-miss — L4가 cf-tunnel을 쓰지만 이건 터널 요청 자체다** (cf-tunnel 관할) |
| 7 | "이 코드 리뷰해줘" | codex-review 관할 — 정적 리뷰 ≠ 실행 검증 |
| 8 | "package.json 만들어줘" | 생성 요청 |
| 9 | "APK 빌드해줘" | 별도 도메인 (APK 스킬 미생성, 보류 중) |
| 10 | "하네스 점검해줘" | **near-miss — '점검'이 겹치지만 대상이 `.claude/`다** (forge P0 관할) |

**경계 조건 도출**: #3·#4·#6·#7·#10이 description의 "~에는 사용하지 않는다" 문장에 반영되어야 한다.

## 3. 채점

- 트리거 판정은 자기 보고가 아니라 **Skill 호출 직접 탐지**로 한다:
  `claude -p "<쿼리>" --output-format json` 출력의 tool_use에서 `omok-verify` 호출 여부 확인.
- 실행 eval은 위 표의 should-act / 불합격 조건을 체크리스트로 채점한다.
- **0% 통과가 나오면 스킬이 아니라 채점 기준의 버그를 먼저 의심한다** — 판정 불가능한 assertion이 흔한 원인이다.
- 수정 후에는 해당 eval만이 아니라 **전체를 재실행**한다(회귀 검출). 1회 1변경.
- 이 스킬은 무인 파이프라인용이 아니므로 pass^3은 요구하지 않는다 — 대화형 1회 통과로 충분하다.
